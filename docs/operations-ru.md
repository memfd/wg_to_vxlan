# Развёртывание и проверка пары мостов

[English](operations.md) · [Описание коллекции](../README-ru.md)

## Выбор двух узлов

Скопируйте пример inventory в локальный файл. В группу `ovirt_fabric` включите ровно два хоста. При расширении сети на новый хост второй записью будет действующий узел. Ansible подключается к каждому из них по SSH. При развёртывании каждый хост создаёт локальную пару ключей WireGuard, а Ansible передаёт открытый ключ соседу. При подготовке inventory проверьте ключи SSH обоих хостов. [Пример inventory](../examples/inventory.yml)

| Параметр | Что указать |
|---|---|
| `ansible_host` | Адрес или имя для подключения по SSH с управляющей машины. Настройте `ansible_user` и повышение привилегий для своего окружения. |
| `fabric_public_ipv4`, `fabric_public_interface` | Публичный IPv4-адрес данного хоста и локальный интерфейс для выхода к публичному адресу соседнего хоста. |
| `fabric_bridge` | Существующий Linux-мост выбранной сети ВМ oVirt на данном хосте. |
| `fabric_wg_address` | Уникальный IPv4-адрес внутри туннеля для каждого из двух хостов. Выберите адреса вне используемых гостевых, управляющих и VPN-подсетей. |
| `fabric_wg_interface`, `fabric_vxlan_interface` | Имена интерфейсов, выделенные администратором на каждом хосте для этого соединения. |
| `fabric_wg_port`, `fabric_vxlan_port`, `fabric_vni` | Одинаковые значения для двух узлов. WireGuard принимает зашифрованные дейтаграммы через публичный IPv4. VXLAN использует свой UDP-порт внутри WireGuard. |
| `fabric_wg_mtu`, `fabric_inner_mtu` | Значения, которые поддерживают публичный маршрут между хостами и выбранные мосты. |
| `fabric_l2_probe_address` | Необязательный IPv4-адрес за удалённым мостом для проверки ping с хоста. Нужны подходящий адрес на локальном мосту и обратный маршрут. Для моста только с гостевыми интерфейсами выполняйте проверку из ВМ. |

## Новый сервер с одним публичным интерфейсом

На зарегистрированном хосте выберите или подготовьте гостевую сеть через Engine/VDSM, который уже управляет её конфигурацией. На новом сервере до регистрации можно поднять отдельный Linux-мост через NetworkManager. Позже к нему подключится порт VXLAN, поэтому запасная физическая сетевая карта не нужна. Проверьте, что работают `NetworkManager` и `firewalld`, и установите пакеты EL9, предоставляющие `ip`, `nmcli`, `firewall-cmd` и Python-модуль `libnmstate`. Проверьте импорт командой `/usr/bin/python3 -c 'import libnmstate'`.

Пример создаёт на новом хосте **новый** постоянный мост для гостевого трафика. Выберите свободные имена профиля и интерфейса. Сгенерированный локально администрируемый MAC сохраняется в профиле. Подставьте MTU вашей пары узлов до запуска команд. На зарегистрированном хосте укажите в inventory существующий мост, которым управляет Engine/VDSM.

```bash
nmcli -f NAME,TYPE,DEVICE connection show
ip -br link show

bridge_mac=$(python3 -c 'import secrets; print("02:" + ":".join(f"{b:02x}" for b in secrets.token_bytes(5)))')
nmcli connection add type bridge ifname guestlan con-name guestlan \
  ipv4.method disabled ipv6.method disabled bridge.vlan-filtering no \
  802-3-ethernet.cloned-mac-address "$bridge_mac" 802-3-ethernet.mtu 1390
nmcli connection up guestlan
ip -d link show dev guestlan
cat /sys/class/net/guestlan/addr_assign_type
```

Проверьте флаг UP, MTU и MAC-адрес моста. Для заданного явно MAC-адреса файл `addr_assign_type` должен содержать `3`. Пока порты отсутствуют, мост может выводить NO-CARRIER. Укажите `fabric_bridge: guestlan` для этого хоста в inventory. После регистрации и до запуска гостей настройте соответствующую логическую сеть и профиль vNIC в Engine через штатную процедуру настройки сетей хоста. Само создание Linux-моста не регистрирует сеть в Engine. Сверьте параметры моста и повторите проверку коллекции после применения настроек Engine. [Справочник свойств NetworkManager](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/nm-settings-nmcli.html)

## Подготовка сети

1. Назначьте логическую сеть ВМ обоим хостам через настройки сетей хоста в Engine или другим поддерживаемым способом через VDSM. Убедитесь, что выбранный мост имеет тип Linux bridge. Зафиксируйте его порты, MTU и MAC-адрес. Проверьте, что оба сегмента должны получать общие широковещательные запросы и что их шлюз и DHCP согласованы.

   ```bash
   ip -d link show type bridge
   bridge link show
   ```

   Мост должен находиться в состоянии UP, иметь отключённую фильтрацию VLAN и точное значение внутреннего MTU из inventory. Задайте постоянный MAC-адрес средствами владельца конфигурации моста, особенно если мост пустой. Автоматически выбранный MAC принимается, только если он уже принадлежит одному из портов и подключение нового порта сохранит адрес моста.

2. На каждом хосте проверьте маршрут до публичного IPv4-адреса соседа командой `ip -4 route get PEER_IPV4`. Выходной интерфейс должен совпадать с указанным в inventory. Ядро должно выбирать в качестве источника тот же локально назначенный публичный IPv4-адрес, что и в inventory. Публичный интерфейс и мост, несущий гостевой трафик внутри туннеля, должны быть разделены. Между публичными адресами достаточно маршрутизируемого IPv4-соединения.

3. Проверьте настройки внешних межсетевых экранов и фильтров провайдера для обоих направлений. Разрешите **публичному адресу соседа /32** доступ к UDP-порту WireGuard на каждой стороне. Границей доступа гостевого трафика служит выбранная L2-сеть. После подключения удалённый гость сможет обмениваться Ethernet-кадрами и широковещательными запросами наравне с локальным. Учтите это в составе моста и правилах гостевой сети.

4. Измерьте доступный IP MTU публичного маршрута в обоих направлениях и согласуйте внутренний MTU мостов и гостей. Заголовки WireGuard поверх IPv4 требуют 60 байт, а VXLAN поверх IPv4 для одного Ethernet-кадра без тегов требует ещё 50 байт. При публичном MTU 1500 задайте WG MTU 1440 и внутренний IP MTU 1390. Для внутреннего MTU 1500 без внешней фрагментации публичный маршрут должен пропускать пакеты IP размером не менее 1610 байт. Дополнительные теги VLAN и уровни инкапсуляции требуют больше места. Изменение MTU логической сети может затронуть других гостей и хосты, поэтому согласуйте его в oVirt до настройки туннеля.

## Применение и проверка

Заполните `inventory.local.yml` и запустите оба playbook на управляющей машине.

```bash
ansible-playbook -i inventory.local.yml wg_to_vxlan.ovirt_l2.site
ansible-playbook -i inventory.local.yml wg_to_vxlan.ovirt_l2.verify
```

До создания туннеля предварительная проверка сверяет inventory, маршрут к соседу и выбранный мост на обоих хостах. Коллекция сверяет содержимое установленных профиля, файлов VXLAN и служб systemd. Если обнаружен конфликтующий интерфейс, чужой файл или переопределение службы, устраните конфликт до повторного запуска. Для изменения peer, VNI или моста запланируйте окно обслуживания, выведите соединение по инструкции ниже и разверните его с новыми параметрами.

Проверочный playbook контролирует связность WireGuard, правила firewall и присоединение локального VXLAN к мосту. На каждом хосте можно проверить эти уровни отдельно командами ниже. Подставьте свои имена интерфейсов, если используете другие.

```bash
wg show wgfabric0
ip -d link show dev vxfabric0
bridge link show dev vxfabric0
bridge fdb show dev vxfabric0
```

После обмена трафиком на обеих сторонах должен появиться свежий handshake WireGuard. Сверьте удалённый адрес и VNI интерфейса VXLAN. В поле master должен находиться нужный мост. Успешный ping внутри WireGuard подтверждает работу зашифрованного IP-соединения. Для проверки передачи Ethernet-кадров подключите по тестовой ВМ на каждом хосте к выбранной логической сети. Назначьте им разные адреса одной подсети, разрешите ICMP в гостевых политиках и проверьте ping в обоих направлениях. Проверьте MAC-адрес соседней ВМ командой `ip neigh` внутри гостей и посмотрите таблицы коммутации на хостах. При внутреннем MTU 1390 команда ping для IPv4 с параметрами `-M do -s 1362` проверяет полноразмерный пакет без фрагментации.

За шифрованный интерфейс отвечает `wg-quick@INTERFACE.service`. Таймер восстанавливает подключение VXLAN-порта, когда мост снова доступен, в том числе после перенастройки хоста VDSM. Для имени интерфейса из примера состояние таймера можно посмотреть командой `systemctl status wg-to-vxlan-overlay-vxfabric0.timer`. После плановой перезагрузки или изменения сети в Engine повторите `verify` и тест между ВМ. Перед тестовой миграцией гостя сначала убедитесь в обычной связности ВМ по туннелю.

## Поиск причины сбоя

| Наблюдение | Что проверить |
|---|---|
| После ping отсутствует handshake WireGuard | Адреса узлов, маршрут через публичную сеть в обоих направлениях, разрешение UDP на обоих узлах и в firewall провайдера. |
| WireGuard передаёт пакеты, но гости не обнаруживают друг друга | Локальный и удалённый адреса VXLAN внутри туннеля, VNI и порт назначения, firewall на WG-интерфейсе, поле master и сеть vNIC на каждом хосте. |
| Маленькие ping-пакеты проходят, крупный трафик зависает | Текущие MTU интерфейсов и гостевых ОС, доступный MTU публичного пути в обоих направлениях. Повторите из гостей проверку с запретом фрагментации. |
| Связь пропала после изменения сети на хосте | Существование моста с прежним именем, состояние служб systemd и фактическое присоединение VXLAN к мосту. |
| Посторонний ARP-трафик, дубли ответов DHCP или широковещательный шторм | Второй L2-путь, конфликт IP-адресов, второй DHCP-сервер или конкурирующий шлюз в объединённом сегменте. |

## Вывод соединения из эксплуатации

Если туннель уже развёрнут коллекцией с прежним именем, сначала выведите его из эксплуатации по инструкции той версии, затем разверните его заново. У новой коллекции другие имена файлов и служб systemd, а также метки принадлежности интерфейсов.

Переведите гостей на другой путь или запланируйте окно обслуживания. Зафиксируйте имена интерфейсов, службы коллекции, внешний допуск в firewall и действующий inventory. Перед удалением VXLAN-порта данной пары отключите и остановите таймер этого порта и остановите связанную с ним службу. Затем отключите службу WireGuard для данной пары, удалите относящуюся к ней конфигурацию и выделенные допуски firewall. Проверьте прежние мосты на обоих хостах. Сохраните или удалите выделенный закрытый ключ по правилам вашей организации. Этот ключ понадобится для восстановления того же WireGuard peer. Для изменения параметров уже созданного профиля требуется плановое переключение. Прежде чем убирать общее правило, проверьте, какие ещё службы используют соответствующий публичный UDP-порт или зону firewall.
